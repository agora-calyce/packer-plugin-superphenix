# Packer plugin for Superphenix — design

## Scope
- Go plugin (`packer-plugin-sdk`): **builder** `superphenix` + **post-processor** `superphenix-export`.
- Builder: creates the VM from a cloud image (`source_url`) or installs from an ISO (`iso_url`), provisions through SSH (Linux) or WinRM (Windows), stops it.
- Post-processor: exports the disk as qcow2 to the machine running Packer, through a helper VM.
- Auth: API token (header `Authorization: api-token <token>`, created in the console) via a masked CI variable. Hand-written HTTP client (no public Go SDK).
- Network: the runner reaches the VMs' **private IPs** (builder and export helper). It must sit in the Superphenix subnet, or behind a VPN. Exposure through an EIP is not supported.
- Distribution: GitHub Releases, `packer init` (`PACKER_GITHUB_API_TOKEN` if the repository is private). The release pipeline (`.github/workflows/`, `.goreleaser.yml`) has not run yet (see `release/README.md`).
- Validated end to end, export included: Ubuntu cloud image, Ubuntu Server 26.04 ISO, Windows Server 2025 FR.

## Superphenix API used
Base: `{api_url}/{orgId}/api/spx-ctrl/{az}/{projectId}/...`. Spec: `https://docs.superphenix.net/assets/openapi/superphenix-api.json` (source: `internal/superphenix-api/api/docs.go` in super-phenix/superphenix).

| Need | Endpoint |
|---|---|
| Create a disk | `POST /disk` (`storage` = integer in GiB, `storageClass` required, `source.type` = `http` or `blank`, lowercase) |
| Wait for import | `GET /disk/{id}` → `disk.status.phase == "Succeeded"` |
| Create VM / helper | `POST /instance` (`network` required, `compute.memory` = quantity string `"4Gi"`, labels `user.superphenix.net/<key>:<value>`) |
| IP / state | `GET /instance/{id}` (`vmi.status.interfaces[].ipAddresses`, `vm.status.printableStatus`) |
| Stop | `GET /instance/{id}/stop` (returns before the actual shutdown: wait for `Stopped`) |
| Detach a disk | `GET /disk/{id}/unmount` |
| Attach a disk | at VM creation only: `disks[].eid` |
| Delete | `DELETE /instance/{id}`, `DELETE /disk/{id}` |
| VNC console | `GET /instance/{id}/vnc` (WebSocket, one session at a time) |

Things to know:
- `cloudInit.custom = true` **replaces** Superphenix's cloud-init (which creates the `spx` user): the plugin creates the SSH user itself, with passwordless `sudo`.
- Deleting a VM does not delete its disks: the plugin creates them separately and deletes them explicitly.
- VM deletion is asynchronous: its disk stays "mounted", and deleting it can return 500, for several minutes. Disk deletion is retried for 10 min.
- A VM that starts before its disks are imported finds nothing bootable: the plugin waits for `Succeeded` on every disk before creating the VM.
- A `http` disk import is done by a Superphenix pod that has **no route to the runner's private IP**: imported URLs must be reachable by Superphenix itself.
- Waits (IP, import, stop) retry transient errors (5xx, network) until their deadline; any other error stops them.
- `compute.memory`: the plugin accepts `4Gi` or `4` and sends `"4Gi"` (API 0.10 and later). On a 400 mentioning `memory` it retries once with the bare integer (older API) and remembers it; this fallback is not tested against a real pre-0.10 API.

## Installing from an ISO
- Disks: a blank disk at `order 0` (`disk_bus`, virtio by default) and the ISO (`http`, `cdrom: true`, `sata` bus) at `order 1`.
- **EFI is required** (`advanced.firmware.bootloader.efi.enabled`): with BIOS (SeaBIOS) only the hard disk is tried and the CD-ROM is never booted. With EFI, the blank disk is not bootable so the ISO starts, then the installed disk boots on its own when the installer reboots: no need to eject the CD-ROM. There is no `bootOrder` in the API.
- `boot_command`: the VNC WebSocket speaks RFB 003.008 ("None" security). The plugin only sends `KeyEvent`s (`internal/client/vnc.go`) through the SDK's VNC driver.
- Answer file: the instance's `cloudInit.config` (`user_data`, a `cidata` disk read by the installer). It avoids Packer's HTTP server, which the VM cannot reach if a security group blocks the runner. `http_content` remains possible.
- Ubuntu 26.04, GRUB EFI: the line `linux /casper/vmlinuz  ---` is the 4th line of the editor; `autoinstall` must be inserted **before** `---` (`<end><left><left><left><left>`: there is one character after the dashes). Check the screen on each new release. `boot_command` is timing sensitive: an unexplained SSH timeout is worth one identical retry.
- The ISO and CD disks stay attached during provisioning, then are detached (`unmount`) and deleted once the VM is stopped.
- Not tested: booting an exported qcow2, Secure Boot and TPM on Linux.

## Windows
- The answer-file ISO is static and hosted (`cd_url`, `example/windows/answer-iso/`: generator and validator), because Superphenix cannot import from the runner. `cd_files`/`cd_content` (ISO generated by the runner) only work if Superphenix can reach the runner; not tested. No `floppy`.
- The answer-file ISO is runner-independent: `windows-initialisation.ps1` (WinRM bootstrap) is on the ISO and found at first logon by scanning the drives (the CD letter varies). The VM never needs to reach the runner; Packer connects to it over WinRM. No `http_*` for Windows.
- The bootstrap opens WinRM with unencrypted Basic authentication. `stepFinalizeWindows` (`builder/finalize.go`, after `StepProvision`, before `stepStop`) runs when `winrm_final_username` is set: creates that administrator, clears the auto-logon registry password and registers a one-shot startup task (SYSTEM) that turns Basic off and deletes the build account and profile at the first boot of a deployed VM (doing it during the build would cut Packer's session). The password goes in an uploaded script that deletes itself, never on a command line. Without `winrm_final_username`, `windows-cleanup.ps1` (run last) only turns Basic off.
- WinPE of the Server 2025 FR ISO: Shift+F10 opens `X:\sources>`; no curl, no certutil, no PowerShell; AZERTY keyboard (VNC sends US keycodes); ~10 min of loading (`<wait600s>`).
- `vm_type = "windows.2k25"` sets EFI, Secure Boot and TPM: without explicit `efi`/`secure_boot`/`tpm`, the builder does not send `advanced`. System disk on SATA (`disk_bus`), no virtio driver during installation.
- User guides: `docs/windows.md`, `docs/linux.md`.

## qcow2 export
1. The builder has stopped the Packer VM. `unmount` its disk, then delete the VM (the disk survives).
2. Create the helper's boot disk (`http` cloud image) and wait for its import.
3. Create the helper VM (its image must differ from the build image: identical filesystem labels/UUIDs make it mount the wrong disk): cloud-init (`qemu-utils`, ephemeral SSH user key, host key), boot disk + Packer disk as second volume.
4. SSH to the helper's private IP: detect the exported disk (neither the helper's root nor the cloud-init disk, unless `disk_device` is set), `qemu-img convert -O qcow2`.
5. Check the free space of the output volume against the qcow2 size (only known after the conversion; check skipped on Windows runners), then download through SSH stdout into `output_path.part`, renamed to `output_path` on success (an existing `output_path` is refused at `Configure` unless `-force`). A stream stalled for 60 s is resumed (20 times at most); a local write error stops at once.
6. Delete the helper, then the disks. Everything is in `defer`s: it also runs on failure or cancellation (Ctrl-C closes the current SSH connection, also one opened by a resume, and removes the `.part` file).

The helper's SSH host key is generated by the plugin (ed25519), injected through cloud-init `ssh_keys` and pinned (`ssh.FixedHostKey`). Until cloud-init has installed it the dial fails on a mismatch and is retried. The private key travels in the helper's user data (API payload), acceptable for a VM that lives for one export.

## Known limits
- If Packer is killed (SIGKILL, runner crash), resources already created remain: the `user.superphenix.net/created-by:packer*` labels make them easy to find.
- A `POST /instance` that times out client-side (60 s) leaves a VM whose ID is unknown to the plugin: same label search.
