# Changelog

## 0.1.2 - 2026-11-13

### Documentation
- Windows guide: new "The final account" section (the two cases, what is deleted or disabled at the first boot, what the logon screen shows).

### Security
- Windows, `winrm_final_username`: the built-in administrator (`Administrator`/`Administrateur`) kept the throwaway build password set by the answer file and stayed enabled in the image. It is now disabled with a random password when the final account is another one (when the build account itself is the built-in administrator, the first-boot startup task does it).

### Fixed
- Windows, `winrm_final_username`: the deleted build account still showed on the logon screen, from its `UserTile` cache entry (a tile per SID), which the first-boot startup task did not clear. It now removes it (0.1.1 announced a logon-screen cleanup that did not cover this).
- Windows, `winrm_final_username` set to the built-in administrator (`Administrator`/`Administrateur`) made the build fail, because the account already exists. The plugin now sets its password to `winrm_final_password` and enables it. The account is found by SID, so the language does not matter.

## 0.1.1 - 2026-11-13

### Breaking changes
- Windows answer-file ISO: `BOOTSTRAP_URL` is removed. The WinRM bootstrap is on the ISO, so it no longer depends on the runner (no IP, port or security group rule; `http_directory`/`http_port_*` are no longer needed for Windows). `make-answer-iso.sh` variables are all optional; `WIN_USERNAME` now defaults to `packer` and `PASSWORD` to a throwaway `Packer-build-1`. Regenerate your ISOs, and set `winrm_username`/`winrm_password` to match.

### Security
- Windows: with `winrm_final_username`, the image no longer keeps the build account, its auto-logon password (Winlogon registry) or the unencrypted Basic WinRM: all are removed at the first boot of a deployed VM.

### Added
- Builder: `winrm_final_username` / `winrm_final_password` (WinRM): after the provisioners the plugin creates this administrator account, removes the auto-logon password and schedules the deletion of the build account (and its logon-screen entry) at the image's first boot. Validated on Windows Server 2025 (French ISO), without the export.
- Docs and example: `example/windows` uses the final account; the answer-file ISO is runner-independent and can be customized (`LOCALE`, `TIMEZONE`, `IMAGE_*`, ...) at generation time.

## 0.1.0 - 2026-11-12

### Breaking changes
- `superphenix-export`: removed `eip_eid` and `runner_cidr` (Packer reports them as unknown arguments). EIP exposure is no longer supported: Packer must run inside the Superphenix subnet, or behind a VPN, to reach the helper's private IP, as it already does for the builder.
- `superphenix-export`: an existing `output_path` is refused unless Packer runs with `-force`. `helper_image_url` must no longer be the build image (duplicate labels/UUIDs make the helper mount the wrong disk): the examples and docs now use a Debian image for the helper.
- `make-answer-iso.sh`: the environment variables `USERNAME` and `HOSTNAME` are renamed `WIN_USERNAME` and `WIN_HOSTNAME` (the old names were often already set by `sudo`, Docker or the desktop session).
- Builder: `secure_boot = true` with `efi = false` is rejected.

### Security
- Post-processor: the helper's SSH host key is generated by the plugin, injected through cloud-init and pinned. It was not verified, so any host answering on the helper's IP could serve the image.
- Windows example: `windows-cleanup.ps1` registers a one-shot startup task that turns off the unencrypted Basic WinRM opened for the build. Images built before this keep it enabled.

### Added
- Builder: `boot_command`/`boot_wait` are accepted with `source_url` (typed on the VNC console of an image without cloud-init). They were rejected without `iso_url`; configurations that do not set `boot_command` are unaffected.
- Builder: ISO source (`iso_url`, `iso_disk_size`, `efi`, `secure_boot`, `tpm`): empty disk + ISO CD-ROM, UEFI, `boot_command`/`boot_wait` typed over the VNC console, `http_content`/`http_directory`. The ISO disk is removed at the end of the build. Tested with Ubuntu Server 26.04.
- Builder: Windows (tested with Server 2025 FR): `cd_url`/`cd_disk_size` (hosted answer-file ISO), `cd_files`/`cd_content`/`cd_label` (generated ISO, needs a runner reachable by Superphenix and xorriso), `disk_bus`, WinRM communicator. `vm_type` keeps its own EFI/Secure Boot/TPM defaults.
- Builder: `user_data`. With `source_url`, extra `#cloud-config` merged with the plugin's cloud-init. With `iso_url`, passed as is (answer file for an installer, no network needed).
- Post-processor: the free space of the output volume is checked before the download.
- Docs: user guides (`docs/linux.md`, `docs/windows.md`), `example/windows/` (template, answer-file ISO generator and validator).
- Release pipeline (GitHub Actions, goreleaser, GPG-signed checksums), untested until the first tag: see `release/README.md`.

### Fixed
- Post-processor: the qcow2 is downloaded to `output_path.part` and renamed on success; a failed download no longer deletes a previous image.
- Post-processor: Ctrl-C during a download resume now closes the new connection instead of finishing the whole download.
- Builder: instance deletion retries 5xx/network errors (2 min); when it still fails, disks are no longer waited on for 10 minutes and the leftover IDs are reported.
- Builder: `ssh_host` and `winrm_host` are honoured (the VM's private IP is only the default).
- Builder: an explicit `efi = false` is sent to the API instead of being dropped when a `vm_type` is set.
- Builder: the address served to the VM (cd.iso URL, `HTTPIP`) is always IPv4.
- `user_data` merge keeps YAML 1.1 booleans (`lock_passwd: no`) as written instead of turning them into strings.
- Superphenix 0.10: `compute.memory` is sent as a quantity string (`"4Gi"`), with a fallback to the integer on a 400 from an older API.
- Builder: resources are always deleted when a build does not complete, and an artifact is returned only when the last step completed (a cancellation could leave the VM and disks behind, or return an artifact for deleted resources).
- Builder: with `source_url`, the instance is created once the disk import has finished, as with `iso_url`.
- Builder: fails at once when Packer's cache directory (`PACKER_CACHE_DIR`) cannot be created, instead of hanging in the SDK's retry loop and filling `/tmp` with logs.
- Waiting for an IP, a disk import or a stop retries transient API errors (5xx, network) until its deadline. Disk deletion does the same for up to 10 minutes.
- Post-processor: the parent directory of `output_path` is created.
- Post-processor: a local write error (full disk) stops the export at once instead of being retried as a network stall.
- Post-processor: a failed reconnection while resuming the download reports its error instead of crashing.
- Post-processor: the helper boot disk carries the `created-by` label, like the helper VM.
